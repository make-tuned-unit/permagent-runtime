# Jev as a new programming primitive — research notes (in progress)

Started 2026-09-21. Budget ~40 reads via gh CLI + WebFetch.

## Status: Area 1 done, Area 2/3/4 in progress

### mgaitan/sqlite-jev (2 stars, pushed 2026-09-18, no license listed)
SQLite loadable C extension + Python wheel. Key API:
- `jev_rows(table_name, question [, kind [, criteria [, columns]]])` — TABLE-VALUED FUNCTION. Batches up to 40 source rows into ONE shared state, asks one question per row, returns virtual table with `source_rowid, answer, probability, choice, score, confidence`, joined back via rowid. THIS IS THE KEY PRIMITIVE: batching MANY ITEMS against ONE question in one state (not one item many questions) — worth checking against the "batching several items in one state corrupts absolute scores" caveat; sqlite-jev docs don't flag that risk.
- Scalar fns: `jev(state,cond[,threshold])` bool, `jev_prob`, `jev_choice`, `jev_score`, `jev_score_norm`, `jev_confidence`, `jev_eval` (raw JSON), `jev_stats()`, `jev_cache_clear()`, `jev_version()`.
- Config via `jev_config('model'|'batch_size'|'max_rows'|'timeout'|'api_url'|'api_key', ...)`. `max_rows` = hard SPEND GUARD — scan aborts before sending if over limit.
- Caching: connection-local only (not persisted to disk) — lost on reconnect.
- README ships a COMPARISON TABLE vs 3 sibling projects it read on 2026-09-18:
  - `mattn/sqlite3-jev`: scalar-only SQLite ext, but documents a **local tensai-compatible endpoint** (local-model swap-in) and multi-question batching via `jev(state, questions_json)`.
  - `EugeneBoondock/jevsql`: Node.js/CLI over SQLite, adds match/candidate-extraction/"review bands", and — uniquely — **persisted decisions + refresh history + audit receipts** (provenance/audit trail as a first-class feature, not just cache).
  - `realZachi/pg-jev`: Postgres extension, PL-Python, executor read-ahead batches 20 rows automatically at the query-execution level (batching is transparent to the query writer, not something you ask for).
- [MEASURED-ish, self-reported by project, not independently verified] CI: mock tests + scheduled live smoke test every 2 months.

### kylemclaren/jevql (11 stars, MIT, pushed 2026-09-19)
"Semantic SQL for vanilla PostgreSQL" — NOT a Postgres extension. A Go CLI/REPL (`jevql`, psql-shaped) that parses SQL client-side with libpg_query, strips `jev_*` predicates before sending to Postgres, executes judgments itself, and re-applies filter/group/sort/limit in-process. No CREATE EXTENSION, no superuser.
- SQL surface: `jev(alias,'condition'[,threshold])` bool; `jev_prob`, `jev_choice(alias,q,ARRAY[...])`, `jev_score`, `jev_score_norm`, `jev_confidence`, `jev_eval`.
- Real example queries in README are the standout creative material:
  - `WHERE jev(meetings, 'could have been an email')`
  - `WHERE jev(commits, 'is apologising for something')`
  - `jev_choice(reviews, 'what is the reviewer really upset about?', ARRAY['food','service','price','parking','other people'])`
  - `jev_score(wines, 'how pretentious is the tasting note?', ARRAY['plain','flowery','insufferable'])`
  - `WHERE jev(jobs, 'is really a sales job despite the title')`
  - `WHERE jev(tickets, 'the customer says they already restarted it')`
  - GROUP BY on `jev_choice(...)` result — semantic GROUP BY.
- Architecture pipeline: **Collect** (parse SQL, strip jev predicates, extend SELECT list) → **Judge** (canonicalize+dedupe row JSON, local sqlite cache keyed by `sha256(model+kind+question+options+canonical_row_json)`, batch 40/req, concurrency 6) → **Project** (apply filters/group/sort/limit in the CLI).
- `--explain` shows cost/row-count BEFORE spending — a dry-run cost estimator, notable pattern.
- Hard v1 limitations are explicit and instructive: no jev in INSERT/UPDATE/DELETE/DDL, no jev in CTE/subquery/HAVING/window fn, no `OR jev(...)` (only AND), no comparing `jev_prob(...) > 0.7` directly (must use threshold arg), no SELECT DISTINCT, no set ops, no bytea columns unless narrowed. This is a real engineering account of what breaks when you try to put a semantic judgment into general relational algebra: it composes cleanly under AND/filter/sort but NOT under set-algebra, aggregatable-before-judged operations, or update-in-place.
- Cache is persistent (sqlite on disk, cross-session) unlike sqlite-jev's connection-local cache.
- Footer example: "jev: 129 judged, 4 req, 82 cache hits, 21.0k in tokens, $0.0009, 1.02s" — visible unit economics per query.

### keltokhy/jlink (3 stars, MIT, pushed 2026-09-21 — updated TODAY)
Record linkage for economists. NOT a SQL layer — Python/CLI/Stata/R library for entity resolution.
- API: `jlink.link(left, right, entity="firm", on=[("conm","assignee"),"state"], definition="<plain English match rule>", left_id=..., right_id=...)` → `.links` (id, id, p=match probability, margin), `.report()`, `.methods()` (auto-written paragraph for a paper's data appendix — target audience is literally academic economists).
- Pipeline: **Block** (cheap local candidate generation: ngrams, initials, exact, window — zero API cost) → **Judge** (Jev scores each candidate pair against the plain-English rule) → **Resolve** (one-to-one/many-to-one/etc via optimal assignment, threshold + margin-over-runner-up) → **Audit** (`audit_sample(200)` draws a stratified calibration sample for hand-labeling → precision/recall/calibration table with CIs).
- [MEASURED, self-reported benchmarks dated 2026-09-18, Jev 1.13 via OpenRouter, 5 public linkage datasets]: jlink F1 beat best-tuned string-similarity baseline on 4/5 datasets (firms 0.73 vs 0.69, DBLP-ACM 0.996 vs 0.975, Abt-Buy 0.92 vs 0.86, Amazon-Google 0.66 vs 0.64) and underperformed only where corruption was character-level typos, not semantic (FEBRL4: 0.96 jlink vs 0.998 TF-IDF). Cost: 146,119 candidate pairs for $2.49 total (~$0.000017/pair), ~250-260 pairs/sec at 64 concurrent calls, median latency 214ms.
- CALIBRATION FINDING (important, matches known Jev limits): "calibration does not transfer" is borne out empirically — probabilities were well-calibrated at the extremes (>0.8 true 95-98%, <0.2 true ~0.1%) but the middle band (0.5-0.8) was OVERCONFIDENT on one dataset (mean 0.64, actually true only 39%) and UNDERCONFIDENT on another (FEBRL4 0.2-0.5 band actually true 66%). Their advice: "Treat p as a strong ranking and check the middle band with an audit sample."
- Idempotence/reproducibility: every probability is stored/cached; rerun costs nothing, returns identical links; saved runs retain input fingerprints + blocker params + model identity for provenance.
- Rule sensitivity anecdote: firm-matching rule tuned once after reading a 300-record pilot's errors (added "CPY means Company") — moved F1 by 2 points. This IS the "materialized column that needs recomputation when wording changes" problem in miniature — but jlink treats the wording itself as a versioned research artifact (goes in the paper's methods section) rather than something to silently cache-invalidate.
- Explicit budget semantics: `budget=0` = cache+exact-shortcuts only, `budget=None`=unlimited, positive budget stops new requests at observed cost (in-flight calls can overshoot).
- Data-governance warning up front: raw `on` fields leave the machine to an external API — explicit "do not use on confidential/restricted-use data" warning.

### keltokhy/jsort (9 stars, MIT, pushed 2026-09-21 — updated TODAY)
"sort, but the key is a description." CLI (`jsort`, part of a `jgrep`/`jsort`/(jlink? shares cache format) family from keltokhy).
- NOT full pairwise O(n^2): shows Jev two texts at a time ("Text A ranks higher than text B on this criterion: '...'"), asks about only a FEW pairs per text (default k=10, i.e. ~n*k/2 comparisons, not n²), fits a **Bradley-Terry scale** to the win-probabilities, sorts by fitted score. This is the actual answer to "how many comparisons, how is inconsistency handled" from the brief: it's a statistical ranking model over sparse pairwise judgments, not a comparison sort.
- Real demo: FOMC press-conference statements ranked "more hawkish about inflation" — 51 sentences, 255 comparisons/10 rounds, reliability 0.96, cost $0.0037/7.2s. Whole-document version: 95 FOMC statements 2011-2026, ranks 2022 75bp hikes at top, pandemic-era at bottom, by-chair averages (Bernanke -2.19, Yellen -1.29, Powell 0.62, Warsh 2.32) — a validated-against-known-history demo of scoring as measurement, not just classification.
- Rigor tools: **standard error** per score (robust/sandwich logit regression with leverage correction), **reliability** (split-half Spearman-Brown correlation — "below 0.8 jsort says so: raise -k, or the description is not one these texts can be ranked on" — i.e., it can detect when a dimension is NOT well-defined/orderable for the data), **first-position lean** (bias-correction for order effects in the pairwise prompt, estimated like home-field advantage, doesn't bias the score).
- **Anchored scales** (`--save-scale`/`--scale`): solves the "can't compare two different runs" problem — saves ~30 anchor texts (verbatim, so scale files leak data) + description + exact question wording + model ID; later texts are placed by comparison ONLY against the anchors (not full resort), and the scale refuses to load/save if answers came from a mix of models (tracks per-answer model provenance) — this is a genuine "semantic index that can be incrementally maintained" pattern, exactly what the brief speculated about.
- Cache shared across the keltokhy tool family (jgrep/jsort/jlink), keyed by endpoint+model+question+row, with model provenance tracked per cached answer.
- Question wording as literally the sort comparator: "Write the description as a comparative... it goes into one question, `Text A ranks higher than text B on this criterion: \"...\"`"

### keltokhy/jselect (3 stars, MIT, pushed 2026-09-21)
Not asked for by name in brief numbering but part of same family — RAG-without-vectors context selector. `jselect(records, task=..., tokens=8000)` finds relevant passages for a task within a token budget, favoring "different information over repetition" (novelty-aware selection, not just top-k similarity). Notable: `--sample representative` mode explicitly separates "find leads" (default: most relevant + most different) from "measure a population" (uniform random draw over the relevant set, with reproducibility guarantees down to the bit) — a rare explicit acknowledgment that semantic retrieval for exploration and semantic retrieval for unbiased measurement are different tools. Full-scan cost is preflighted against a dollar budget before any calls are made (never silently degrades to a cheaper shortlist).

### realZachi/pg-jev (270 stars — by far the most starred repo touched, MIT-ish/"PostgreSQL" license, pushed 2026-09-18, has a marketing site pgjev.com)
The most mature/most-adopted of the SQL layer. `CREATE EXTENSION jev CASCADE`; `jev(table,'condition')`, `jev_prob`, `jev_score`, `jev_choice`, `jev_confidence`, `jev_eval`, `jev_stats()`, `jev_cache_clear()`. Composes as an ordinary boolean function with AND/joins/GROUP BY/ORDER BY.
- Architecture: on first call for a table+condition, starts a **read-ahead** that streams the table in physical order via TID range scans (constant memory regardless of table size); batches `jev.batch_size` (default 20) rows into one shared JSON state with one Noul question per row each; up to 2×`jev.concurrency` requests in flight over persistent HTTPS; **LIMIT stops the read-ahead early**; predicates evaluated before jev() in the WHERE clause correctly prune rows before they're ever judged (cost-aware query composition).
- [MEASURED, in-repo, 2000-row EU dataset]: batch size 20 vs 40 vs 80 accuracy test against ground truth — **batches of 1-20 rows: 100% correct; batches of 40: 92-98%; batches of 80: 77-94%**. This is a DIRECT, quantified confirmation of the brief's stated caveat "batching several ITEMS in one state corrupts absolute scores" — pg-jev's own authors measured the corruption curve and set the default batch size (20) below where it starts to degrade. They explicitly ruled out two fixes that didn't help: wider rows (1000 chars) made no difference at 20; naming rows instead of indexing them did not help either.
- Cost/perf numbers: first run of the 2000-row/100-request query ≈3.5s, ~296k tokens, ~$0.012; cached rerun ≈50ms; LIMIT 3 on a new condition ≈0.6s. Notes a real regression fix: v0.1.0 needed 8.5s/338k tokens for the same query, current is faster — i.e. batching cuts cost/time by >2x.
- Caching: per-row-content, session-scoped (lost on disconnect, same limitation as sqlite-jev).
- Ships an agent skill (`.agents/skills/pgjev/SKILL.md`) on skills.sh for automated install (`npx skills add realZachi/pg-jev`) — docs are agent-readable via `.md` suffix on any doc URL, a "for agents" doc page exists.
- CAVEAT it states outright: managed Postgres hosts without superuser/plpython3u (Supabase, Neon, RDS) cannot run it — architecturally tied to self-hosted/superuser Postgres, unlike jevql's client-side-CLI approach which needs neither.

### DuckDB extensions — multiple competing/possibly-fake forks found (search turned up 7 "duckdb-jev"-adjacent repos in one week — matches brief's warning about AI-generated forks flooding the space). Picked the two substantive ones:

**colliber/duckdb-jev** (MIT) — "typed Jev answers as real SQL types." Cleanest API of everything found:
- `jev_choice(text, MAP{option: meaning})` → real `ENUM` column typed from the criteria itself
- `jev_score(text, [worst,...,best])` → `DOUBLE`
- `jev_noul(text, MAP{'true':meaning,'false':meaning})` → `DOUBLE` probability
- `jev_ask(text, {name: criteria, ...})` → `STRUCT`, **one request carries many named questions about one row**, each field typed from its own criteria, choice/score fields get a companion `<name>_confidence` column.
- Type/argument errors (empty option map, duplicate option, non-constant criteria, >255 options) fail AT QUERY PLANNING TIME, not at row 400,000 — pushing Jev's constraints into the SQL type checker.
- `jev_usage()` table function reports requests/cache_hits/input_tokens/output_tokens live.
- Explicit gotcha: DuckDB evaluates a function once per place it appears in a query, so an unguarded call in both WHERE and SELECT bills twice per row unless CTE'd.

**yodablocks/jev-orderby-bench** (0 stars but the single most valuable find in this area — an INDEPENDENT, reproducible, adversarial measurement suite, not a vendor of a Jev product). "Does ORDER BY over a Jev probability put rows in a defensible order?" Pre-registered gates on 360 human-labeled rows plus a "hard probe" on Amazon ESCI (306 human-graded query-product pairs, 30 hard queries).
[MEASURED, 2026-09-18/19, reproducible for ~$0.013, jev-1.13.0]:
- Easy corpus: **passes all 6 gates** — Boolean ECE 0.045, inversion rate 0.036, Score ordinal inversion 0.143 (against a 0.15 threshold — "the weak link"), negation consistency 0.016.
- Hard probe (ESCI, graded shopping relevance): **fails 4 of 6 gates** — Boolean ECE 0.242, inversion 0.255, Score inversion 0.254 against human grades, 23/30 queries over threshold, choice-confidence ECE 0.279. I.e., Jev's accuracy claims hold on easy/synthetic benchmarks and break down on hard graded-relevance tasks — a genuine, sourced counter-data-point to vendor claims.
- **CRITICAL, independently confirms pg-jev's own finding**: re-running the SAME 360 rows through recodelabs' duckdb-jev extension's default 40-row batching (vs 1-row-per-request) **fails the ranking gate it otherwise passes**: inversion rate jumps from 0.036 (1/request) to 0.171 (batch 40), Spearman correlation with the unbatched baseline drops from ~0.93 to **0.579** (bool) / **0.506** (score). This is a second, independent lab reproducing the exact "batching corrupts absolute scores" phenomenon the brief warned about, with numbers.
- **Output quantization finding (new, not in the brief's stated limits)**: Jev returns probabilities at only 2 decimal places. Over 360 rows this produced only 45 distinct Boolean-probability values; 21.6% of all row pairs tie exactly; 53 rows tie at the top value 0.99. Consequence: `ORDER BY prob DESC LIMIT 20` returns an ENGINE-DEPENDENT, non-reproducible sample of a 53-way tie, not a ranking — every one of the SQL extensions' README examples using this exact pattern is silently affected. Mitigation order given: treat LIMIT as `WHERE prob >= threshold` (accept the whole tied group), break ties with a second more specific question, or at minimum add a deterministic secondary sort key.
- Systematic **underconfidence** direction found (mean signed calibration gap +0.042, 8/10 bins above the diagonal) — benign for ranking (order preserved) but means naive `WHERE prob > 0.9` is stricter than it reads (true rate at predicted 0.855 is actually 0.914).
- Negation-consistency finding: the touted `P(q)=1-P(not q))` check (0.016 median violation) is NOT actually measuring negation-specific behavior — a same-meaning paraphrase control disagrees by an almost identical 0.0159, so the "good negation consistency" number carries no information beyond general wording-sensitivity noise. Good methodological catch, worth stealing as a pattern: always run a paraphrase control alongside a negation control.
- Vendor's own published number: 67.8% agreement vs averaged frontier-model judgments, self-run, unreproduced [UNVERIFIED beyond that self-report] — https://evals.typesafe.ai/.

## AREA 2: control-flow DSLs / semantic types

### carldaws/hunch (MIT, Ruby/Rails)
`Hunch.chance("written by a real human, not spam", given: bio)` → probability. Named threshold levels as verbs: `possibly?` (>=0.25), `likely?` (>=0.5), `probably?` (>=0.75), `almost_certainly?` (>=0.93) — configurable per-level. `pick(:ham,:spam, given: email)` classification; `rate(:calm,:frustrated,:livid, given: email)` → object with `.level`, `.position` (continuous), and `>=` comparison operators overloaded directly on the ordinal scale (`mood >= :livid`). `Hunch.decide(given: x) { |q| q.probably? :urgent, "..."; q.pick :team, ...; q.rate :mood, ... }` batches multiple typed questions about one state into one call, returning a result object with per-field probabilities/labels. Real Rails patterns shown: ActiveRecord `validates` calling `Hunch.likely?` as a validation predicate (with `rescue Hunch::APIError; nil` — fail-open on API failure so an outage never blocks unrelated validations), inbound-email routing by classifying subject+body, and error triage picking ignore/notify/page by rating severity. This is the cleanest "semantic value as an ordinary language value" implementation found — booleans, symbols and comparables, not JSON blobs.

### Kelbie/hunch (different project, same name — MIT, Node/CLI)
NOT a control-flow DSL — a semantic code-search + review-rule tool ("Semantic code review with Jev, plain-English rules and Agent Skills"). `hunch find "Does this code turn a failed operation into a successful result?" --mode condition` searches a repo chunk-by-chunk via Jev and returns scored source locations for an agent to then read and verify — explicitly NOT a proof: "Search scores rank candidates; findings flag configured concerns. Neither proves a bug or the absence of one." `hunch check --all --pack nuts-spec` runs a published rule pack against any repo with no clone/config; PR review via GitHub Actions/App reads policy from the immutable base commit (can't be edited mid-review to dodge a check). Relevant to Area 4 (semantic lint) more than Area 2 despite the name collision — worth flagging the naming collision itself: THREE unrelated "hunch" projects exist (carldaws/hunch Ruby DSL, Kelbie/hunch code search, and a "tpellet/hunch" mentioned in passing by Augustus) plus "huncho" below — a sign of how fast people are converging on the same metaphor independently.

### edgardcham/huncho (MIT, TypeScript, npm `huncho`, has a full docs site) — ★ best-engineered control-flow DSL found
"A hunch is a probability with a policy attached." Vendor-neutral: works with Jev direct, Jev via OpenRouter, Jev via Vercel AI Gateway, or a custom factory — nothing above the "model seam" knows which vendor answered.
```ts
const route = huncho("support.route", { model: jev() })
  .ask({
    urgent: noul("Does this need a human within the hour?"),
    topic: choice("What is it about?", ["billing", "bug", "other"]),
  })
  .when((a) => a.urgent.p, { enter: 0.8, exit: 0.6 }, "page")
  .when((a) => a.topic.is("billing", 0.7), "billing")
  .else("triage");

const decision = await route.decide(text, { key: "T-1041" });
decision.outcome;   // "page" | "billing" | "triage"
decision.via;       // "enter" | "hold" | "else" — HOW the outcome was reached
decision.previous;  // what this key decided last time
```
Key mechanisms (exactly what the brief asked to find in source, described in docs):
- **Hysteresis** as a first-class primitive: `{ enter: 0.8, exit: 0.6 }` — a decision enters state "page" only above 0.8 and, once in, stays there until probability drops below 0.6, keyed per-entity (`key: "T-1041"`) so different tickets don't share state. This is a direct, deliberate defense against a noisy/flapping probability signal near a naive fixed threshold — the single most concrete anti-flakiness pattern found in the whole survey.
- **Nested decisions** — decisions can compose (docs page exists, not fully read).
- **Journal + replay**: every decision is journaled; "replay a policy change without inference" — i.e. you can change the threshold/policy and replay historical judged probabilities against the NEW policy without re-calling the model, because the probability (the judgment) and the policy (the threshold/hysteresis) are stored as separate objects. This is exactly the brief's "materialized column" idea taken further: the semantic judgment is cached permanently and only the cheap policy logic is re-run.
- **Calibration + sweep**: "Closing the loop" doc: decide → label outcomes → calibrate → sweep → "a threshold read from the journal instead of picked by hand" — i.e. thresholds are fit from historical labeled journal entries, not guessed.
- Compile-time type safety: `a.topic.p("refund")` is a TYPE ERROR because "refund" isn't one of the declared choice options — answer shape is derived from the question shape at the type level.
- Explicit "stability" doc and frozen public API since 0.1.0 (currently 0.6.0) — a versioning/backward-compat discipline notably more mature than most of the survey.
- Python port "next," sharing one fixture set across languages so journals are interchangeable between the TS and Python implementations.

## AREA 3: learning from feedback

### sutro-sh/jev-align (Apache-2.0, from Sutro, "AI Functions from human feedback using Jev and GEPA")
"AI Function" = a saved, portable, versioned artifact bundling: the accepted question/definition text, input signature, runtime backend (TypeSafe/Vercel Gateway/Cloudflare Workers AI), learning config, and the full labeled dataset (splits + optional rationales) — but explicitly NOT raw unlabeled source rows or credentials. Loop, every round: (1) evaluate the dataset, measure UNCERTAINTY per row; (2) select the most ambiguous rows + a random audit sample for a human to label; (3) run GEPA (a prompt/definition optimizer, reflection-model-driven) over accumulated labels+rationales to propose a revised question/definition; (4) show score delta, certainty change, and a diff of the proposed definition; (5) human explicitly accepts/rejects/rewinds — "a higher training score never accepts a proposal automatically." **What GEPA optimizes: the QUESTION/DEFINITION TEXT itself** (confirms brief's speculation) — not the option descriptions separately, the whole task definition as one artifact. Task types: binary, multiclass, multilabel, score(ordered rubric). Config: 5/10/15/20 labels per round, optional 20% held-out eval set, GEPA metric-call budget defaults 300. Production feedback loop: `AIFunction.load(path, capture=True)` records live production inputs for later labeling — closes the loop from deployment back into training. Public registry ai-functions.dev for sharing/forking functions (pull with no login; owner can unpublish, reversible). This is the most complete "prior art" for the brief's "a person's own past decisions become a tiny local model of their judgment" idea — though it optimizes a PROMPT via GEPA, not a distilled local weight model (that's Luce, next).

### scienthoon/luce (Apache-2.0) — ★ direct evidence for "personal judgment becomes a tiny local model"
Trains an actual small local model (LoRA + decision head on Qwen backbone, e.g. Qwen3-4B-Base) to answer the same three Jev-style typed questions (Choice/Score/Noul) with NO text generation at inference — closest thing in the whole survey to "your own judgments become a tiny local replica." Pipeline: `luce init "<task in one sentence>"` → `luce synth` (generate/annotate training data via any OpenAI-compatible teacher, or label real data, or relabel after a policy change) → `luce train` (LoRA + decision head, picks bi/isolated/label training mode) → `luce eval --real <labels>` (fits temperature/calibration against real labels — explicitly refuses to report calibrated numbers without real labels: "every number Luce prints is tagged [in-synth]" otherwise) → `luce serve` (`POST /v1/ask` with `state` + typed `questions`, returns probability per option, queues low-confidence answers for human review).
[MEASURED, dated, in-repo, reproducible]:
- Rule-based ticket task (priority defined by an undisclosed rule = template+anger+tier, 5% label noise, ceiling ~95%): Luce (3B + LoRA on 8,100 synthetic tickets) beat both same-size zero-shot prompting AND Jev zero-shot on every axis — priority accuracy 97.3% (Luce) vs 34.3% (3B prompting) vs 44.7% (Jev) — because the rule is NOT recoverable from the text alone; a model has to be trained on outcomes to learn it. ECE 0.003 (Luce) vs 0.105 (prompting) vs 0.107 (Jev).
- Public-benchmark generalization test (trained on ARC-Easy+BoolQ only, evaluated on 3 unseen datasets): Luce roughly matches/slightly beats same-size prompting on 2/3, Jev still wins outright (86-94% vs Luce ~64-80%) — Jev's larger/broader training shows through on genuinely novel semantic tasks. Their own stated conclusion: **"Calibration does not transfer"** — an INDEPENDENT confirmation of the brief's stated known limit, both for Luce's own head (refit temperature 2.5-3.3, overconfident on unseen tasks) and for Jev itself (refit temp 2.74 on the rule task Jev never saw).
- Practical rule stated: ship with 100-300 real labeled items; without real labels every reported number is untrustworthy/unlabeled-as-such.
- Explicit finding: accuracy CAN transfer reasonably (2/3 unseen datasets) even when calibration does NOT — a nuance worth carrying into the final report.
Also cites (not independently verified here): TechCrunch 2026-09-18 quote "Almeida says Jev is trained exclusively on synthetic data" [UNVERIFIED, secondhand attribution] — if true, is a striking claim about Jev's own training methodology.

## AREA 4: semantic tests / lint

### supercorp-ai/supercov (MIT, "Code quality and coverage for coding agents")
Two separable halves: (1) **quality**: `npx supercov quality` asks Jev a fixed set of ~12 named yes/no questions per source file (long_method, deep_nesting, complex_conditional, + 9 more unnamed in the truncated README) and does score arithmetic itself locally so "every part of a score is a claim you can check against the file" — i.e. the aggregate score is auditable back to individual boolean judgments, not an opaque number. Cost ~1 cent/MB, content-addressed caching so reruns only pay for changed files. Output literally reads "Quality weak (3.8/10) over 163 files... weak runtime/python/supercov_runtime.py: long_method 0.96, deep_nesting 0.92, complex_conditional 0.89, +9 more" — per-file, per-check probability breakdown. (2) **coverage**: runs the project's OWN test command unmodified, instruments it (lines/branches/MC-DC/optional-chain paths), and turns uncovered paths into small "obligations" an agent can target one at a time, with `diff <run> latest` to prove a new test closed a specific gap — this half uses NO Jev at all, pure instrumentation; Jev is only in the quality half.
- Built explicitly as an "agent loop" tool: designed prompts tell a coding agent to run supercov, pick ONE gap, write ONE focused test, rerun, and verify the diff — a genuine example of a typed judgment gating/directing autonomous agent iteration rather than a human reading a report.
- "Assertion maps": agent-filled semantic descriptions of what each test assertion checks, separately validated — Rust owns mechanical validation/change-tracking, "the agent supplies semantic reasoning" — an explicit human/agent-vs-mechanical division of labor around a Jev-adjacent judgment.

### DanRWilloughby/snifftest (MIT) — "AI writing tells" prose linter
Splits rules into **countable** (regex, free, local, always scores 1.00 — dashes, colon-heavy paragraphs, uniform sentence rhythm, banned words) vs **judgment** (needs reading, not counting — "not X but Y" constructions, tricolon cadence, stacked hedging, rhetorical-question openers, a closer that just restates the paragraph, self-undercutting marketing copy, "first X that" claims, a cost figure with no comparison, employment claims, a pull-quote with no verb — 15 total rules, 10 general + 5 marketing-only opt-in). Judgment rules send ONE PARAGRAPH AT A TIME, one probability per rule, explicitly "no general model in the loop... and it will not rewrite your text. A flag is a sentence for you to fix" — deliberately scoped OUT of generation.
- **Dead-zone / abstention pattern worth stealing**: readings between 0.4-0.6 are reported as "no judgment" and NEVER become a flag or a pass — "That band exists because the judgment model answers about 0.5 on text it cannot read, and a flat middle number is the one failure that looks like a clean draft." This is a concrete, deliberate abstention mechanism layered on top of a model that (per the brief's stated limits) "does not abstain by itself" — the tool builds abstention by treating the uninformative middle band as a non-answer rather than trusting the raw number.
- Consent gate: "the first time, it prints exactly what it is about to send and where, and waits for your answer" before any judgment call is made — explicit opt-in per project, not per invocation.
- `--dry-run` runs zero-cost countable rules only, nothing leaves the machine.

### coldteadotai/abide (MIT, npm `@coldtea/abide`) — ★★ best "semantic test/CI gate" implementation found, and the ONLY one in this survey with an independently-reported precision/recall number against human review
"Coding agents break your rules from the very first edit. Abide catches every one and makes your agent fix it." Hooks into Claude Code / Codex / OpenCode. On every edit (or every turn), sends Jev ONE question per project rule (sourced from AGENTS.md/CLAUDE.md — rules "no linter can check," e.g. "never let a raw error reach a user," "don't create premature abstractions") plus the diff — explicitly NOT the conversation, so "edit 200 is checked like edit 1" (no context-window degradation). Verdict bands: **>=0.8 → agent is told to repair automatically, no human in the loop; 0.5-0.8 → shown to the human only, agent not blocked; <0.5 → nothing.**
[MEASURED, in-repo benchmark, dated by pushedAt 2026-09-20, cost disclosed]: replayed 93 real Claude Code sessions (1,256 edits, 147 turns) across two real repos against their own actual AGENTS.md rules, for **22 cents total**. Jev flagged 39 edits and 15 turns; an independent human reviewer confirmed 10/15 turn-level catches (single-use abstractions, oversized files, duplicated logic) — roughly 73% precision on the turn-level judgment, with full methodology and a per-rule table published at benchmarks/replay/README.md. Their explicit economic argument for why this wasn't done before: a check costs ~2,500 tokens; at ordinary LLM prices that's a cent+ and several seconds PER EDIT with free-text output you then have to parse and half-trust — "200 edits a day made it a non-starter." Jev: "up to 100x cheaper... about 300ms" is what makes per-edit gating economical.
- **`abide calibrate`**: scores every rule against the repo's own recent git history (20 real hunks) and auto-disables rules that score ~0.4 on everything (never fire — badly worded, non-discriminating question). **`abide tune`**: has the agent itself rewrite rules that never fire. **`abide audit`**: judges an entire existing codebase as if every file had just been written (33 API routes, 12 seconds, ~1 cent). The compiled rubric (`.abide/rubric.json`) is a committed, human-readable artifact where "every verdict names a rule in it, and every rule quotes the line of your instruction file it came from" — full provenance from natural-language project rule to typed question to verdict.
- Directly relevant to this user's own "review gate & UI consolidation" and "harness improvement loop" memories: this is an existing, working, measured implementation of exactly the "typed judgment as a CI/agent gate" pattern the brief asked whether anyone had built.

### frostney/clean-code-review (MIT, built on `eve` + Next.js + Vercel AI Gateway, live demo deployed)
Judges every changed file in a PR against a Robert C. Martin *Clean Code* question set via Jev, then a separate chat model ("Luna", `openai/gpt-5.6-luna-fast`) writes prose review from the structured answers — a clean two-stage architecture: **Jev judges (typed, checkable), a chat model narrates (prose, not itself authoritative)**. "Jev answers with probabilities and scores rather than sentences, so a verdict is made of things a reader can check against the code." Question SET IS PER-FILE-TYPE: e.g. a "Boy Scout Rule" question only fires on diffs, a "has tests" question only on test paths — a plain source file gets fewer questions than a test diff. Explicit epistemic disclaimer: "The decision and the paragraphs are model output shaped by the submitted code: read them as advice, never as authorisation to merge."

### dannote/jev (Elixir/OTP, Hex.pm package, 24 stars)
"Jev is a peer process. You reply to it from a GenServer, and its answer is a message you pattern match on." `Jev.Server` behaviour: `handle_call` sends typed questions (Noul/Choice/Score, inferred from criteria shape: string→Noul, {q,map}→Choice, {q,list}→Score) asynchronously; `handle_answer/3` clauses pattern-match on the returned probability/confidence map with GUARDS as thresholds: "Clause order is the routing. Thresholds are guards." e.g. `def handle_answer(%{security: p}, from, s) when p > 0.5, do: ...`. Non-blocking: "a hundred calls can be in flight, and each answer finds its clause when it lands." Because `handle_answer/3` is a pure function of a literal map, it's trivially unit-testable with no network. This is the actor-model equivalent of huncho's typed-decision-tree pattern — genuinely elegant for a Rust-daemon-with-actors-style architecture (message arrives, pattern-match/guard on the typed judgment, route).

### innocentdiaz/s1_ruby (2 stars — very new/tiny but conceptually the most novel language-integration found)
"AI built for interfacing with code... The AI race has revealed the operation that computation was missing: `collapse` over meaning." Explicitly borrows the quantum-measurement metaphor: a `ψ` (psi) operator prepares an unmeasured **state** from data (`ψ people`); asking a question is "measurement"; reading a boolean is "collapse", and — the genuinely new idea — **collapse can be deferred**: distributions from multiple judgments can be combined with overloaded logical operators (`&`, `|`, `~`) and range checks BEFORE collapsing to a concrete boolean, and `undecided?` is a first-class predicate for values that haven't been (or can't confidently be) collapsed. Also overloads Ruby's `Enumerable` directly: `people.max_by(&ψ.score("How skilled?", "novice","competent","expert","exceptional"))`, `.select`, `.group_by`, `.sort_by`, `.sum`, `.grep` all accept a judgment as the block. A "lens" (`given:`/`against:`) supplies the rubric to judge relative to, rather than the model's own undefined sense of a term. This is the most literal realization of the brief's "a semantic judgement becomes a cheap, typed, repeatable VALUE that ordinary code can branch on, store, index, sort by" — sort_by and grep taking a judgment block directly is exactly that value-ness made syntactically native.

### abhixhek/jevcal (10 stars) — calibration/threshold-fitting + CI drift gate
"Stop guessing confidence thresholds. jevcal measures a typed decision model on *your* data, picks the threshold that meets *your* accuracy target, tells you how much traffic still needs an LLM, and fails CI when a model update quietly breaks it." Workflow: describe decisions in `questions.yaml` (same shape as the TypeSafe API) → run against a held-out labeled split → jevcal reports, per question, the confidence threshold that hits a target accuracy, what fraction of traffic that threshold can handle vs. must escalate to a slower/smarter model, and ECE. Ships a full **cascade cost model**: e.g. demo shows 85.4% of rows escalate to an LLM at the chosen thresholds, saving only 14.4% vs LLM-only — a realistic accounting that a naive "just call Jev, it's cheap" pitch would hide when the ACCURACY BAR is strict. Explicit note: cannot publish real Jev benchmark numbers due to TypeSafe's customer agreement restricting published performance numbers — ships a deliberately-overconfident simulator for the demo instead [notable, somewhat concerning constraint on independent verification of Jev claims generally]. **CI-gate framing directly answers the brief's "recomputation when wording changes" question**: jevcal is designed to be re-run whenever `jev-latest` (a moving alias) or the question wording changes, and to fail the build if the previously-tuned threshold no longer meets the target — treating a calibrated threshold as a versioned, testable build artifact rather than a constant.

## AREA 5: official framing (TypeSafe)

Source: WebFetch summaries (isolated/untrusted per tool contract) of https://typesafe.ai/blog/introducing-system-one-models-and-jev and https://docs.typesafe.ai/llms.txt — treat specific quoted phrases below as [DEMO-ONLY]/vendor marketing, not measured claims.

**Framing / thesis**: explicitly Kahneman System-1-vs-System-2. Vendor's own words (per fetch): traditional LLMs/chat models = System Two (slow, deliberative, prone to hallucination); Jev = System One (fast, typed, non-generative). Core architectural claim: "Jev outputs all probabilities in parallel instead of autoregressively generating by token" — i.e. the whole pitch is architectural (no autoregression = no per-token hallucination surface, not just "smaller/cheaper model"). They claim greater RELIABILITY, not just speed, as the payoff of the non-generative design.

**What it's FOR, per the vendor** (beyond classification): four framed use cases —
1. "AI-Powered Workflows / smart if-statements" — "Structured outputs slot into ordinary software as fuzzy decision rules" — i.e. TypeSafe's own pitch is precisely the brief's "new programming primitive" framing, not merely "a classifier."
2. "Map-reducing over big data... Turn petabytes of data into features and insights" — positions Jev as a bulk feature-engineering/ETL primitive, not just a per-request classifier — consonant with the SQL-layer projects in Area 1.
3. Real-time UX — "100ms speeds means you can use AI in your applications where UX is critical."
4. "Verify everything. Score, judge, verify, guardrail, and detect jailbreaks of LLM prompts" — positions Jev explicitly as a SUPERVISORY layer over other (generative) LLMs, not a peer to them — matches the DataJev/Abide/clean-code-review pattern of "typed judge supervises/gates a chat model" found independently across three unrelated projects.

**Demos led with**: Doom (real-time reactive gameplay — "what can be done with code + AI") and a Wikiracing/Wikipedia-navigation game (high-cardinality decision-making across hundreds-to-thousands of link choices per step) — both demos deliberately chosen to showcase LATENCY and CHOICE-CARDINALITY (Choice supports up to 255 options) rather than accuracy on a benchmark.

**Roadmap**: minimal disclosure — "We have a lot more in the pipeline," no specifics on specialized/fine-tuned/on-device models surfaced in this fetch. [DEMO-ONLY/thin — could not extract concrete roadmap commitments.]

**Docs structure** (docs.typesafe.ai/llms.txt): confirms the three primitives (Choice/Score/Noul) each return probability-per-option/level plus a separate CONFIDENCE figure — docs explicitly frame "confidence as distinct from probability for controlling system behavior" (i.e., two different numbers for two different control decisions: how likely is X, vs. how sure is the model of its own answer — several tools above conflate these, worth noting). Stated design principle verbatim: "keeping code in control and giving System One narrow, structured decisions." Five documented composition patterns: fan-out, confidence-gated routing, composite scoring, intent routing, hierarchical classification — this is TypeSafe's own answer to "control-flow DSL patterns," narrower than what the community built (no hysteresis, no journaling, no calibration-fitting in the official docs — those are all community inventions layered on top). 16 cookbook examples include re-ranking, semantic search, structure recovery, RAG classification, LLM guardrails, and "autoresearch loops" (closest official analog to DataJev's LLM-analyst/Jev-controller split). Docs acknowledge "Jev 1.13 jaggedness" as a named, documented limitation (self-disclosed model imperfections, not just a community-discovered issue) — consistent with jev-orderby-bench's independent finding of quantized/tied probability outputs.
