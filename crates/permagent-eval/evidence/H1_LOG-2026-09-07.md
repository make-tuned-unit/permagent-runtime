## A/B-able knobs (traced to a live read on the `permagent run` path)

The decisive finding: **every config key is an env var.** `Config::get_param`
(crates/goose/src/config/base.rs:910-922) checks `env::var(key.to_uppercase())`
before the config file, with no cache. Mapping is `foo_bar` → `FOO_BAR`.

**Trap:** `parse_env_value` tries `serde_json::from_str` first, so `FOO=1` for a
`get_param::<bool>` key deserialises as a *number*, fails the bool conversion,
and falls back to the default. Booleans must be `true`/`false`. Knobs read with
a raw `std::env::var` parser accept `0`/`1`. The registry encodes which is which.

Registered in `ab::KNOBS`:

| knob | var | default | read at |
|---|---|---|---|
| repo-map | `PERMAGENT_CODING_REPO_MAP_TOKENS` (0 disables) | 4096 | goose-cli/src/session/builder.rs:666,709-711 |
| premature-done-guard | `PERMAGENT_AFTER_TURN_HOLD` (raw, 0/1 ok) | on | goose/src/after_turn.rs:153-159 |
| reviewer-mandate | `REVIEWER_MANDATE` (get_param bool) | on | goose/src/after_turn.rs:380-384 |
| tool-pair-summarization | `GOOSE_TOOL_PAIR_SUMMARIZATION` | on | goose/src/context_mgmt/mod.rs:25-28 |
| lessons | `PERMAGENT_LESSONS_ENABLED` (raw) | off | goose/src/lessons/mod.rs:139-143 |
| librarian-atoms | `LIBRARIAN_ATOMS_ENABLED` | off | goose/src/agents/platform_extensions/ext_manager.rs:644-649 |
| acr | `PERMAGENT_ACR_MODE` (off/precision/completeness) | off | goose/src/brain_handle.rs:1827-1890 |

Deliberately EXCLUDED, with reasons in the `KNOBS` doc comment:
- `PERMAGENT_BEST_OF_N_ENABLED` / `PERMAGENT_BEST_OF_N` — read
  (cost_router/best_of_n.rs:76-81,382-392) but `run_best_of_n_sampling`
  (best_of_n_adapter.rs:247) has no caller outside its own tests. Flipping it
  compares a configuration against itself.
- `MAX_HOLDS`, `CODE_MAP_INJECT_MAX_CHARS`, `OFFLOAD_TOKEN_THRESHOLD` — hard consts.
- numeric levers (`GOOSE_AUTO_COMPACT_THRESHOLD`, `GOOSE_TOOL_CALL_CUTOFF`,
  `GOOSE_MAX_TURNS`, `GOOSE_CONTEXT_LIMIT`) — real, but no natural on/off pair;
  `--a-env`/`--b-env` covers them.

### Correction to the DAG note

The memory says "repo-map/localization PARTIAL — `code_map_instructions_block`
reaches ONLY goal dispatch, not the main loop". That is true of the *orchestrator*
mechanism, but INCOMPLETE: there is a **second, separate** repo map on the
`permagent run` path — the coding-harness session builder's
(`goose-cli/src/session/builder.rs:666-747`), env-tunable via
`PERMAGENT_CODING_REPO_MAP_TOKENS` and ON by default at 4096 tokens. Two gates:
the recipe title must match `is_coding_harness_recipe`, and a remembered
`coding_repo_map_{hash}` config key can override it (harmless for the eval, whose
runs each get a fresh `PERMAGENT_PATH_ROOT`, hence no remembered answer).

## Tier 0 mechanism

No usable out-of-process fake provider exists: `TestProvider`
(goose/src/providers/testprovider.rs) is compiled in but never registered in the
factory and its `from_env` always errors. So Tier 0 registers a **declarative
provider** in the run's own `$PERMAGENT_PATH_ROOT/custom_providers/`
(declarative_providers.rs:363-379 loads from `Paths::config_dir()`, which honours
`PERMAGENT_PATH_ROOT`) with `engine: openai`, `requires_auth: false`,
`supports_streaming: false`, pointed at a loopback stub server. Non-streaming is
only expressible through a declarative provider — the built-in `openai` hardcodes
streaming — and it reduces the stub to one plain JSON body.

## First conclusive paired A/B — repo-map on deepseek-chat, 2026-09-07

`permagent-eval ab --tier dschat --knob repo-map --repeats 2` against the signed
bundled CLI, keys from the keychain. 17 fixtures x 2 repeats x 2 arms = 68
invocations, 34 runs per arm — ABOVE the honesty guard's 30, so this is the first
verdict in this program rather than another INCONCLUSIVE. Measured spend $2.60
(plus a $0.05 two-invocation probe first, to validate the paid path before
committing 68 runs to it). Raw record: `evidence/AB-repo-map-dschat-2026-09-07.json`.

| | repo-map off | repo-map on | delta |
|---|---|---|---|
| solved | 34/34 (100%) | 34/34 (100%) | +0.0 — **no change** |
| measured $ | 1.3503 | 1.2503 | −7.4% |
| input tokens | 18,505,594 | 18,876,300 | +2.0% |
| cache-read tokens | 16,825,984 | 17,408,640 | +3.5% |
| tool calls | 772 | 731 | −5.3% |
| median seconds | 75.6 | 75.3 | flat |

**Repo-map is a cost/cache lever here, not a correctness lever.** The H0 research
ranked localization the top SWE-bench lever on Agentless' evidence (32% on Lite
with no agent). On a model that already solves this suite the correctness effect
is absent, and what remains is ~7% cheaper at ~2% MORE input tokens — the saving
comes from cacheability, not from sending less.

Against the excellence gates, stated exactly:

- Coding success: 34/34 = 100%, clears the >=90% bar. ONE qualifying run; three
  consecutive are required.
- Cost routing: gate is >=20% better USD/solved. 7.4% — real and directional but
  does NOT graduate the area.
- Token efficiency: gate is >=20% fewer input tokens. This is 2% MORE. Fails.
- Latency: flat, and harness overhead is still not separated from model time, so
  the gate remains unevaluable rather than passed or failed.

**The suite is saturated and that is now the binding limit.** 100% in both arms
means these 17 fixtures cannot detect a correctness effect on any capable model;
every future pass-rate delta measured here is uninformative by construction. A
weak local model (qwen2.5:7b) DID show a large apparent pass-rate effect, which
is precisely the trap: the same knob reads as decisive or irrelevant depending on
model strength, and only a paired run at the right strength separates them.
Harder tasks are the prerequisite for any further correctness claim, which is
what the unbuilt `huggingface-benchmarks.yaml` path (SWE-bench subsets,
Terminal-Bench) exists to supply.

Local-arm note: the same sweep could not complete on this machine. Two attempts
were killed for low memory — swap 14 GB of 15.4 GB used and 5.58M pageouts
BEFORE any run started — and the two-machine 27B split needs 16.6 GB, so it is
further out of reach. A remote provider needs no local memory and is what made
the measurement possible at all.

## Second conclusive paired A/B — premature-done guard on glm-4.7, 2026-09-07

`permagent-eval ab --tier glm47 --knob premature-done-guard --repeats 2`.
34 runs per arm, above the honesty guard's 30. Measured spend $3.72.
Raw record: `evidence/AB-premature-done-guard-glm47-2026-09-07.json`.

| | guard off | guard on | delta |
|---|---|---|---|
| solved | 32/34 (94.1%) | 33/34 (97.1%) | +2.9 pts — **improved** |
| measured $ | 1.3318 | 2.3838 | +79% |
| input tokens | 7,030,871 | 12,328,004 | +75% |
| output tokens | 96,811 | 200,174 | +107% |
| tool calls | 357 | 634 | +78% |
| median seconds | 62.7 | 149.5 | +138% |

**Read the effect size, not the verdict.** The whole +2.9 points is ONE fixture:
`merge-row-2048` went 1/2 to 2/2. Every other fixture was identical in both arms.
The tool renders a directional verdict because the sample clears its 30-run bar,
but what was actually bought is a single passing run out of 34, at +79% cost and
+138% latency. On this evidence the guard is a poor default for a model of this
strength; it is not evidence that the guard is worthless, because a single task
flip is also within the noise the same framework warns about elsewhere.

**Correction to the previous entry.** I generalised from deepseek-chat that "the
suite is saturated for capable models". That is too broad: glm-4.7 scores 94.1%
here, so these fixtures DO discriminate for it. Saturation is per-model, and the
right statement is that the suite cannot discriminate for deepseek-chat, which
solved 34/34 in both arms of the repo-map comparison.

**What the two verdicts together say about the shipped defaults.** Both knobs are
ON by default. repo-map earns its place: no correctness change, ~7% cheaper.
The premature-done guard does not, at this model strength: it nearly doubles cost
and more than doubles latency for one task in thirty-four. Making it conditional
on model strength — or on task risk — is the obvious follow-up, and is exactly
the kind of routing decision the cost-router already exists to make.

Gate status after two conclusive runs: coding success has one qualifying run at
100% (deepseek) and one at 94.1%/97.1% (glm), so it does NOT have three
consecutive qualifying runs and the 90% bar is met but unstreaked. Cost routing
still fails its >=20% bar. Token efficiency fails outright. Latency remains
unevaluable while harness overhead is not separated from model time.
