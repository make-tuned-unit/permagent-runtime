# Home UI research — 15 October 2026

## Scope and evidence

Research for a personal-agent desktop Home in the 2025–2026 product context. Sources below are official product documentation checked on 15 October 2026. These are documented interaction patterns, not controlled usability studies or proof of higher productivity. Some patterns predate 2025 and remain useful; no release-year claim is implied. Apple's JavaScript documentation exposes limited text to the reader, so its indexed official excerpts supplement the pages. Notion's English Home URL currently redirects to sidebar documentation; its localized Home documentation still describes the widgets.

The live-app crawl was blocked. Computer Use discovered Permagent but returned “Computer Use was not approved to use Permagent”. The requested AppleScript fallback returned error -10827; screencapture reported that the specified rectangle did not intersect any displays. Only the supplied `crawl/00-home-top-live.png` is live visual evidence. Lower Home and the other tabs were assessed from source, not seen live. No screenshot has been invented.

## Synthesis and design decisions

These are design inferences from the patterns, not claims that the products mandate this layout.

1. **Hierarchy follows questions:** what needs my decision, what is on my day, what has my agent been doing? Use that order in the DOM and on screen.
2. **One concept in one place:** Decisions owns the pending queue, Calendar owns appointments, To-dos owns dated tasks, In flight owns active goals, and Recent conversations owns past conversations. Connection state stays in the header. Remove repeated rankings and totals from the default.
3. **A disciplined grid:** two equal columns for peer cards, a full-width decision summary, natural row sizing, one spacing rhythm. Dense masonry fills holes but can change reading order and strand whitespace; reserve it for legacy custom arrangements. Collapse to one column based on content width, not screen width.
4. **Progressive disclosure:** one specific decision headline is sufficient to explain the review count; the inbox owns all candidates and approval controls. Calendar expands to its full view. Full lists and specialist cards remain available through existing navigation and customization.
5. **One primary action:** Review decisions. The neutral empty state offers an ordinary inbox link; errors offer Retry. Do not fabricate urgency or keep a prominent review button when there is no pending decision.
6. **Honest empty states:** loading, unavailable, zero pending, blocked goals, and recent activity are distinct. Never show “all clear” for a failed request. Never manufacture a suggested task or a successful outcome. Keep empty cards compact.
7. **Plain, short, general copy:** Decisions, Today, Activity, Calendar, To-dos, In flight, Recent conversations. Use actual titles and counts. Avoid personal names and model vendors in new copy. Backend terms belong in details when needed.
8. **Accessibility:** real buttons, descriptive names, existing focus/escape behavior, no color-only status, wrapping long titles, and scrollable capped lists. Preserve theme and reduced-motion tokens rather than adding cosmetic animation.

## Evaluation criteria

At the supplied 1258×902 window size, the first viewport should explain the decision queue and expose the day section without a status strip. A zero-data Home must be compact and truthful. Busy lists must remain reachable without card overlap. On a narrow content area, sections retain their order in one column. Existing custom layouts must not be overwritten merely by viewing Home. Test exact default recognition, template selection, empty/error states, and the shared review entry point; inspect actual browser renders if execution is available.
